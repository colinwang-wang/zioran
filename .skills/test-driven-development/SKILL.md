# Test-Driven Development (TDD)

## 触发条件
实现任何功能或 bug 修复时，写实现代码之前。

## 铁律
**没有先写失败测试，就没有生产代码。**

## RED-GREEN-REFACTOR 循环

### 1. RED — 写失败测试
- 写一个最小的失败测试，明确展示预期行为
- 一次只测一个行为
- 命名清晰：`Test_购买课程_余额不足时返回错误`

### 2. 验证 RED
- **必须**看到测试因正确原因失败（特性缺失）
- 如果因拼写错误、import 缺失等原因失败 → 修正后重新验证
- 如果测试意外通过 → 你在测试已有行为，修正测试目标

### 3. GREEN — 最少代码通过
- 写**最少**代码使测试通过
- 不超前实现、不添加"以后可能需要"的代码
- 允许丑陋，只要测试绿

### 4. 验证 GREEN
- 当前测试通过
- 所有已有测试也不断

### 5. REFACTOR — 清理
- 消除重复
- 改进命名
- 提取辅助函数/公共逻辑
- 保持所有测试绿

## 关键原则

| 规则 | 处理方式 |
|------|----------|
| 在测试前写了代码 | 删除代码，从头开始 |
| 测试意外通过 | 你在测试已有行为，修正测试 |
| 想保留"参考代码"或"适配代码" | 禁止，未经测试的实现一律删除 |
| 测试很难写 | 这是接口设计的信号，先改设计再写测试 |

## 良好测试标准

- **最小化**：一个测试验证一个行为
- **命名清晰**：读测试名就知道在验证什么
- **使用真实代码**：优先真实依赖，非必要不 Mock
- **独立**：测试之间无顺序依赖
- **快速**：单个测试毫秒级完成

## 实践流程示例

```
1. 需求：用户购买课程时扣减金币

2. RED:
   func Test_购买课程_扣减金币(t *testing.T) {
     svc := NewOrderService(db)
     // 用户余额 100，课程价格 20
     err := svc.Purchase(userID, courseID)
     assert.NoError(t, err)
     assert.Equal(t, 80, getBalance(userID))
   }
   → 运行：FAIL（Purchase 未实现）✓ 正确原因

3. GREEN:
   实现最小 Purchase 逻辑使测试通过

4. 验证：所有测试绿 ✓

5. REFACTOR：提取余额检查到独立方法

6. 下一个 RED：
   func Test_购买课程_余额不足返回错误(t *testing.T) { ... }
```

## 约束

- NEVER：跳过 RED 直接写实现
- NEVER：一次写多个测试再实现
- NEVER：保留未被测试覆盖的生产代码
- MUST：每个 RED-GREEN-REFACTOR 循环完整执行
- MUST：重构阶段不改变行为（测试持续绿）
